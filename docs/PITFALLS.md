# 踩坑记录（PITFALLS）

> 每一条都来自真实调试现场，不是假设。统一按 **现象 → 根因 → 解法 → 可复用规则** 记录。
> 已脱敏：不含真实令牌、Cookie、账号口令、节点 IP 与 tailnet 域名。
> 相关代码在 [`tools/`](../tools)，Tailscale 专题见配套仓库 `tailnet-cookbook`。

## 1. 先体检，再动手（环境探测）

### 1.1 「装好了却跑不起来」：27B 模型加载即被杀
**现象**：模型权重 17 GiB 已完整下载、`ollama list` 能看到，但一请求就 HTTP 500：`llama-server process has terminated: signal: killed`。
**根因**：容器 cgroup `memory.max` 硬限 8 GiB 且无法提升；该规格加载需要 CPU buffer 约 4 GiB + repack buffer 约 11.7 GiB ≈ 15.8 GiB。`oom_kill` 计数为 0，说明是被 cgroup 限额直接干掉，不是内核 OOM。
**解法**：先读 `/sys/fs/cgroup/memory.max`（v1 为 `memory.limit_in_bytes`）算出上限，再决定规格；本环境改用 4b / 1b。
**可复用规则**：**「能下载」≠「能加载」**。任何大模型 / 大索引 / 大编译任务，动手前先 `probe_environment.py` 看 `can_load_*`，别等进程被 kill 才回头查。

### 1.2 无 `/dev/net/tun`、无 systemd
**现象**：Tailscale 报无法创建 TUN；`systemctl` 不存在。
**根因**：容器缺 `CAP_NET_ADMIN`，PID 1 不是 systemd（是 init/shim）。
**解法**：Tailscale 改 `--tun=userspace-networking`；服务全部手动 `nohup ... &` 并写一份「一次性拉起全部服务」的重启清单。
**可复用规则**：安装脚本默认假设「有 systemd + 有 TUN + 有 GitHub」，三者任一不成立就要准备静态二进制 + 手动启动路径。详见 `tailnet-cookbook`。

### 1.3 后台进程「自己没了」
**现象**：长任务跑到一半，Ollama / Web / tailscaled 全部消失，但 `oom_kill=0`。
**根因**：沙箱休眠回收后台进程，不是内存不足。
**解法**：把状态写文件（tailscaled `--state=`、下载分片落盘），并提供幂等重启脚本；所有长任务设计成「重跑即续传」。
**可复用规则**：**不要假设后台进程能活过整个会话**。进程可丢，状态必须落盘。

### 1.4 磁盘只剩 1 GiB 量级
**现象**：下载到一半失败，或解压报 No space left。
**根因**：目标设备（手机 iSH）剩余空间本就紧张。
**解法**：`shutil.disk_usage` 先判 `disk_low`；大文件落到可写且空间足的盘，成功后清理 `.chunks/`。
**可复用规则**：大文件任务第一步是查磁盘，不是发第一个请求。

## 2. 下载与网络

### 2.1 官方安装脚本慢到 14 KB/s
**现象**：`curl ... install.sh | sh` 卡住。
**根因**：安装脚本会 307 跳到 GitHub Releases，而本机到 GitHub 基本不通。
**解法**：用可达的镜像取静态 `tar.zst`，手工解压到 `/usr/local`，绕开脚本对 systemd 与 GitHub 的依赖。
**可复用规则**：安装脚本是「最顺路径」不是「唯一路径」；先看清它到底从哪下载，再决定要不要换源。

### 2.2 单连接 600 KB/s → 并发分片 21 MB/s
**现象**：模型 registry 单连接约 600 KB/s，4b 要下很久，27b 几乎不可行。
**根因**：服务端对单连接限速，但对多连接不做总限速。
**解法**：24 并发 × 8 MiB 分块 + Range，3.12 GiB 用时 2m56、16.22 GiB / 1974 块用时 15m27，峰值约 21 MB/s；按 sha256 命名直接落到目标目录结构。
**可复用规则**：遇到「单连接慢」先试 `Range` 分片，不要先换代理、换 DNS、换协议。`concurrent_range_download.py` 就是这个套路。

### 2.3 用 `Range: bytes=0-0` 代替 HEAD 做探测
**现象**：HEAD 被 CDN 拒绝 / 不返回 `Content-Length`。
**根因**：不少站点只放行 GET，HEAD 直接 403 或空响应。
**解法**：发 `Range: bytes=0-0`；支持的话返回 `206` + `Content-Range: bytes 0-0/TOTAL`，一次请求同时拿到「总大小」与「是否支持分片」。返回 200 则说明忽略了 Range，退化单连接。
**可复用规则**：探测请求要选「最可能被允许」的方法；能一次拿两个信息就别发两次。

### 2.4 镜像站对非零偏移 Range 的表现不一致
**现象**：有的源 `bytes=0-0` 正常，但 `bytes=8388608-...` 返回 200 全量。
**根因**：缓存层只对首个 Range 生效。
**解法**：探测结果只作为「乐观判断」，分片阶段仍逐块校验 `status == 206` 且长度精确匹配；不满足就明确报错并提示 `--workers 1`，绝不把「200 全量」当成一块写进去。
**可复用规则**：服务端声明的能力每次都要在真实请求里复验。

### 2.5 半截文件被误判为「已完成」
**现象**：中断后重跑，直接跳过 certain 分片，最终文件损坏。
**根因**：分片直接写目标文件，中断留下残缺文件但大小恰好「看着差不多」。
**解法**：分片写 `xxx.tmp` → `os.replace()`；每片启动时校验 `size == expect` 才算命中缓存；合并写 `.part`，sha256 通过才 `os.replace()` 成最终文件；校验失败**保留分片目录**供续传。
**可复用规则**：**原子落盘 + 精确长度校验 + 校验通过后改名**，是任何断点续传的最小正确集。

### 2.6 「网络被墙了」的误判
**现象**：`GET /user` 返回 403，于是开始折腾代理、换 DNS、装加速器。
**根因**：该 API 对**未认证**请求本来就返回 403；带上有效令牌后直连就是 200。
**解法**：先做基准对照（带认证 / 不带认证、直连 / 代理），确认是哪一层的问题再动手。
**可复用规则**：**先证伪最简单解释**。403 ≠ 网络不通，可能是「没带凭证」「权限不足」「WAF」。

### 2.7 API 时好时坏
**现象**：同一脚本这次全绿、下次超时。
**根因**：出口链路抖动，不是代码回归。
**解法**：统一 `req()` 封装 3 次重试 + 指数退避 + 40 s 超时；4xx（除 429）不重试，避免把错误请求重放三次。
**可复用规则**：网络代码里重试是基础设施，不是补丁；但要区分可重试与不可重试错误。

## 3. 命令行与 BusyBox 差异

### 3.1 BusyBox wget 不认 GNU 参数
**现象**：`wget --tries=1 --no-verbose --header=X ...` 直接报 usage 错。
**根因**：BusyBox wget 1.33.x 只实现了 `--header 'K: V'`（**两个独立参数**）、`-O`、`-T`、`--post-data` 等少数选项。
**解法**：生成命令时按目标实现分档：默认按 BusyBox 语法输出，只有显式 `--gnu` 才加 `--tries=1 --no-verbose`。
**可复用规则**：**先探测工具实现（`probe_environment.py` 的 `wget_flavor`），再生成命令**。别把桌面 Linux 的经验搬到 iSH / Alpine。

### 3.2 照搬浏览器请求头下到「残片」
**现象**：`Copy as cURL` 生成的命令下出几 KB 的坏文件。
**根因**：播放器发的是 `Range: bytes=0-1`；照搬等于只请求一小段。
**解法**：`STRIP_HEADERS` 自动剥离 `Range` / `Host` / `Connection` / `Content-Length` / `Transfer-Encoding` / `Sec-Fetch-*`。
**可复用规则**：**浏览器复制来的请求头是「那一次交互」的快照，不是「这个资源」的通用描述**。

### 3.3 `Accept-Encoding: gzip` 让 wget 存下压缩包
**现象**：下载成功、文件后缀也对，但打不开。
**根因**：wget 不解压 gzip 响应体，而 curl 带 `--compressed` 会解。
**解法**：剥离 `Accept-Encoding`（让服务端返回未压缩内容），或改用能解压的客户端。
**可复用规则**：转换工具要处理的是**语义等价**，不是参数逐条对应。

### 3.4 手动 `Host` 在重定向后指错主机
**现象**：CDN 302 到另一域名后请求失败。
**根因**：`Host` 被当成固定头带到新主机。
**解法**：逐跳头一律交给客户端自己生成。
**可复用规则**：`Host` / `Connection` / `Proxy-Authorization` 属于连接层，不属于资源请求。

### 3.5 解析 curl 命令必须走 `shlex`
**现象**：手工 split 空格把带引号的 Cookie 切断，或把用户输入拼进 shell 造成注入。
**根因**：shell 词法比「按空格切」复杂得多。
**解法**：`shlex.split(posix=True)`；先处理 bash `\` 续行与 Windows `^` 续行；全程保留参数数组（`subprocess.call(argv)`），不拼字符串。
**可复用规则**：**解析用 shlex，执行用 argv**，两件事都别用字符串拼接。

### 3.6 curl 的 `-d` 不是 GET
**现象**：带 `--data` 的 curl 转成的 wget 命令返回 405。
**根因**：`-d` 隐含 POST，而 wget 默认 GET。
**解法**：识别 `-d/--data*` → 生成 `--post-data`；对不支持 POST 的极简 wget，提供标准库 `urllib` 兜底函数。
**可复用规则**：转换工具要显式处理「方法」这个隐式语义，不能只看 URL 和头。

## 4. HTTP 服务与浏览器兼容

### 4.1 `python3 -m http.server` 播不了视频
**现象**：Safari / iOS 打开 mp4 一直转圈，Chrome 却可以。
**根因**：Safari 先发 `Range: bytes=0-1` 试探；标准库静态服务完全不支持 Range，返回 200 全量，Safari 直接放弃。
**解法**：实现 `206 Partial Content` + `Content-Range: bytes S-E/SIZE` + `Accept-Ranges: bytes`，并支持 HEAD。
**可复用规则**：**移动端视频播放的硬性前提是 Range/206**，与文件大小、编码格式无关。`http_range_server.py` 是最小可用实现。

### 4.2 416 也要带 `Content-Range`
**现象**：越界 Range 时 Safari 报错而不是跳过。
**根因**：416 响应缺 `Content-Range: bytes */SIZE`。
**解法**：不可满足时回 416 + `bytes */SIZE` + `Accept-Ranges: bytes` + `Content-Length: 0`。
**可复用规则**：状态码配套的必填头要一次给全，别只填「看起来最重要」的那个。

### 4.3 CSS 的 `width:100%` 撞上 Python `%` 格式化
**现象**：生成页面时 `ValueError: unsupported format character 'w'` / `incomplete format`。
**根因**：HTML 模板里 CSS 的 `%` 被老式 `"..." % vars` 当成格式符。
**解法**：模板改用 f-string / 字符串拼接，或把 CSS 里的 `%` 写成 `%%`。
**可复用规则**：**模板引擎选一个**，不要把含 `%` 的文本塞进 `%` 格式化；同理含 `{}` 的 CSS 别塞进 `.format()`。

### 4.4 未知 MIME 导致拒绝播放
**现象**：某些文件 Safari 不认。
**根因**：`mimetypes.guess_type()` 返回 `None`。
**解法**：fallback 到 `application/octet-stream`，图片/视频按扩展名补 fallback。
**可复用规则**：所有「猜测型」API 都要写 fallback 分支。

### 4.5 目录穿越与符号链接逃逸
**现象**：`/../etc/passwd` 可能读到根目录外文件。
**根因**：直接 `os.path.join(root, url_path)` 未做规范化。
**解法**：`realpath` 后要求 `full == root or full.startswith(root + os.sep)`；同时拒绝含 `..`、绝对路径、隐藏文件。
**可复用规则**：**路径校验必须在规范化之后**，且要覆盖符号链接。

### 4.6 拖进度条导致服务端刷错误日志
**现象**：用户拖动进度条时 `BrokenPipeError` 一堆。
**根因**：客户端主动断开旧 Range 请求，完全正常。
**解法**：写响应时捕获 `BrokenPipeError` / `ConnectionResetError` 静默返回。
**可复用规则**：区分「协议正常行为」和「错误」，别把前者记成故障。

## 5. 网页解析与反爬（最容易过度设计的部分）

### 5.1 抓取器只拿到「載入中」
**现象**：用通用网页抓取工具读分享页，正文只有 SPA 占位文字。
**根因**：真实内容由 JS 渲染 / 由后续请求填充。
**解法**：拿原始 HTML 与页面内 JS，找到真实数据接口与变量；不要基于渲染后的文本做判断。
**可复用规则**：**先确认你看到的是不是最终 DOM**。

### 5.2 导航头用在 AJAX POST 上触发 WAF 403
**现象**：同一个密码表单，手动提交成功，脚本提交被拦（1020 / blocked）。
**根因**：把 `Sec-Fetch-Dest: document` 等**导航语义**的头带到了 XHR 上，与 `X-Requested-With` 自相矛盾。
**解法**：为 AJAX 单独构造头：剥离 `Sec-Fetch-*`、补 `Origin`、加 `X-Requested-With: XMLHttpRequest`、`Accept: application/json...`、正确的 `Content-Type`。
**可复用规则**：**GET 的头不能直接复用到 POST**。不同交互类型需要不同的头集合。

### 5.3 用关键词判断页面状态，误判率极高
**现象**：正常页面被判成「浏览器验证页」，或「密码错误」被误判成「链接失效」。
**根因**：裸词 `cloudflare` 会出现在正常页的脚本注释里；通用文案「错误」「失败」到处都是。
**解法**：改用**结构化信号**：HTTP 状态、响应 JSON 的字段、表单是否存在、DOM 节点、重定向目标；关键词只作为最后兜底且要限定上下文。
**可复用规则**：**结构化 > 子串匹配**。做页面状态机时，先列出「有哪些可判定的结构」，再写代码。

### 5.4 表单提交还是 AJAX 提交？
**现象**：按 `<form action>` 提交后服务端不认，或返回整页 HTML 而非 JSON。
**根因**：JS 实际拦截了 submit，改成 `POST /session.php` 的 XHR，成功后 `location.reload()`。
**解法**：读页面 JS 找 `$.post` / `fetch` / `XMLHttpRequest`；按真实接口提交，并按 JSON 响应判断成功。
**可复用规则**：**HTML 里的 `action` 只是默认值**，真实行为在 JS 里。

### 5.5 隐藏字段每次 GET 都会变
**现象**：拿第一次抓到的隐藏字段反复重试密码，永远失败。
**根因**：`pp_t` / `pp_n` / `pp_a` 这类字段带时间戳或一次性令牌。
**解法**：**每一次密码尝试都重新 GET 页面**取新字段，再 POST。
**可复用规则**：把「获取令牌」放进循环内部，别提到循环外做「优化」。

### 5.6 前端哈希算法移植
**现象**：服务端校验某个由 JS 计算的字段，Python 实现的值对不上。
**根因**：JS 位运算是 32 位有符号、乘法会溢出，与 Python 大整数语义不同；还常混用 FNV 变体与自定义常量。
**解法**：把 JS 函数原样保留，用 Node 跑出基准值，Python 逐步对照中间值（每步都 `& 0xFFFFFFFF`），直到同一组输入产出同一结果。
**可复用规则**：**移植 JS 哈希 = 双实现 + 逐中间值对照**，不要靠「看起来差不多」的公式。

### 5.7 把装饰图 / 埋点 iframe 当成目标媒体
**现象**：解析出 `ns.html`（GTM iframe）或站点 logo 当视频下载。
**根因**：正则只按扩展名 / `src` 抓，没有区分「资源域名」和「资源用途」。
**解法**：域名白名单（真媒体在 CDN 子域，主域是装饰图）+ 路径黑名单（`icon` / `logo` / `18-plus` / `news_img` / `app` / `ns.html`）+ `og:image` / `preload as=image` 等语义标记加权。
**可复用规则**：**「长得像」不够，要有来源与语义双重过滤**。

### 5.8 Cookie 其实无关
**现象**：花大量时间搬运 `cf_clearance`、PHPSESSID，结果真机上不带 Cookie 也能解析成功。
**根因**：先入为主假设了反爬机制。
**解法**：做一次「带 / 不带 Cookie」的对照实验；先确认变量是否真的相关，再设计传参。CLI 参数也随之从 `--curl` 简化成 `--cookie`，最终证明可省略。
**可复用规则**：**先做最小对照实验，再增加复杂度**。能不加的参数就不要加。

### 5.9 密码候选不要「发散」
**现象**：试图枚举 `1115`、`115`、`119` 等多种写法，可能触发站点「瀏覽次數限制」把链接锁死。
**根因**：把「猜密码」当成越多越好。
**解法**：只生成补零 `MMDD`，默认最近 7 天，且每次尝试间隔、失败即停的策略明确；提供 `--date-days` 让人控制范围。
**可复用规则**：**对有次数限制的端点，候选集要收敛而不是发散**。

## 6. 测试与验证

### 6.1 `set -e` + 管道拿到的是 `tail` 的退出码
**现象**：前面的命令失败了，测试脚本却判为通过。
**根因**：管道退出码默认取最后一个命令；`cmd | tail` 里 `tail` 永远 0。
**解法**：用 `${PIPESTATUS[0]}`，或干脆把结果写文件再断言文件内容。
**可复用规则**：**断言要针对被验证的对象**，不要针对「管道最后一环」。

### 6.2 BusyBox `tar` 往 stdout 不吐数据
**现象**：`tar czf - dir | base64` 在受限设备上拿到空输出。
**根因**：该实现的 stdout 管道行为与 GNU tar 不一致。
**解法**：先生成 `.tgz` 文件，再对文件做 base64 / 传输，最后清理临时文件。
**可复用规则**：跨实现传输数据时，**落文件比走管道可靠**。

### 6.3 离线 E2E 用假 DNS 映射
**现象**：想测解析逻辑，但外部 CDN 不可控、会变、还有限次。
**根因**：测试依赖真实外部状态。
**解法**：本地起一个假 CDN，把资源域名映射到 127.0.0.1，用预存的真实 HTML 片段回放四类页面（无密码视频 / 无密码图片 / 有密码视频 / 有密码图片）。
**可复用规则**：**把外部依赖替换成本地可控副本**，测试才可重复。

### 6.4 先跑语法检查，再跑逻辑
**现象**：测试脚本自己有 `echo` 少闭合引号、`case` 分支引号不配对、断言写得过严，排查半天以为是被测代码坏了。
**根因**：测试代码没做静态检查。
**解法**：Python 用 `py_compile`，内嵌 JS 用 `node --check`，shell 用 `sh -n`；断言先宽松验证「是否走通」，再收紧。
**可复用规则**：**测试脚本也是代码**，先保证它自己是对的。

### 6.5 「上传返回 201」不等于交付完成
**现象**：仓库里文件大小对，但内容莫名是旧版本 / 被截断。
**根因**：只看 HTTP 状态，没读回内容。
**解法**：PUT 后 GET 回来，`base64.b64decode` 与本地原始字节做 `==` 比较，逐个文件打印 `一致=True`。
**可复用规则**：**可验证交付 = 写 + 读回比对**，尤其是走 API 而非 git 时。

## 7. GitHub / 交付

### 7.1 Contents API 更新文件必须带 `sha`
**现象**：第一次 PUT 201，第二次 PUT 422。
**根因**：更新已有文件需要在 payload 里带上当前 blob 的 `sha`。
**解法**：PUT 前先 GET 该路径，取到 `sha` 就塞进 payload。
**可复用规则**：**先读后写**，让脚本同时兼容「新建」和「更新」两种状态。

### 7.2 `content` 必须是原始字节的 base64
**现象**：中文 README 上传后乱码。
**根因**：对「编码后的字符串」再做了一次 base64，或用了有损的文本转换。
**解法**：`read_bytes()` → `base64.b64encode()` → `decode('ascii')`，全程不碰文本编解码。
**可复用规则**：二进制路径上不要引入文本编码。

### 7.3 公开前先脱敏
**现象**：想把经验分享给其他 Agent，却可能把节点 IP、账号、Cookie 一起公开。
**根因**：实战记录里天然带着环境细节。
**解法**：建仓默认 `private`；确定公开时，把 IP 泛化成 `100.x.y.z`、域名泛化成 `*.ts.net`、凭证一律删掉，并全文搜一遍 `ghp_` / `password` / `token`。
**可复用规则**：**脱敏是发布流程的一步，不是写作时的自觉**。

## 8. 凭证与数据安全

### 8.1 对话里出现过的凭证要当作已泄露
**现象**：调试过程中贴过 PAT、SSH 口令、代理账号、`cf_clearance`。
**根因**：聊天记录、日志、临时文件都可能留存。
**解法**：任务结束后撤销 / 重置这些凭证；脚本只从环境变量或 0600 权限文件读令牌，从不硬编码、从不回显。
**可复用规则**：**凭证的生命周期止于任务结束**；`--show-secrets` 必须是显式开关。

### 8.2 整理用户文件时的四条硬约束
**现象**：Agent 被要求「帮忙整理目录」，风险远大于看起来。
**解法**：默认 dry-run；只 `shutil.move()`（代码里没有任何 `remove`）；目标同名则跳过不覆盖；认不出的进 `_unsorted` 不猜用途；隐藏文件与 `.git` 一律不碰；生成 `undo.sh` 与索引 README。
**可复用规则**：**用户说「不整理」就别整理；说「系统文件不碰」就一个字节都别碰**。可回滚性比分类准确度重要。

### 8.3 `undo.sh` 不能只写本次移动清单
**现象**：第二次执行 `--apply` 后，回滚脚本被覆盖成空，之前移动的文件再也回不去。
**根因**：回滚信息来自「本次 session 的内存」而非「磁盘上的真实状态」。
**解法**：每次都**扫描当前已归类目录**重新生成 undo，并用 `[ -e 目标 ] || mv ...` 防止覆盖用户后来新建的同名文件。
**可复用规则**：**回滚依据要来自持久状态**，不能来自易失的上下文。

### 8.4 用户说「速战速决」时别再堆方案
**现象**：已经实测出可行路径，还在解释 403 / Cloudflare / 各种假设，反复换方向。
**根因**：把「穷举可能性」当成了严谨。
**解法**：锁定已验证的通道（例如 curl 命令 → wget 命令）直接落地，不再发散。
**可复用规则**：**有一条实测通过的路就先走通**；解释留给事后的复盘文档。

## 附：把坑变成资产的三个习惯

1. **每次失败都留一条结构化记录**：现象 / 根因 / 解法 / 可复用规则，而不是只记「修好了」。
2. **把解法收敛成单文件工具**：能 `--help`、能 `--json`、能 import，下次直接复制而不是重新推导。
3. **交付带校验**：下载比 sha256，上传比字节，整理给 undo，服务给 healthcheck。
